# ZMT Live Server (C# desktop v5.4.0)

The new Live Server button on the mobile tool catalog opens a dedicated connection dashboard. It is independent of all legacy per-module URLs and the old device-trust pairing. On the PC open Live Server, select its Tailscale IPv4 adapter, port 8790, and start. On the phone enter the copied URL and current session code. Both devices must be on the permitted tailnet. Keep the port private; do not use Funnel or port forwarding. The protocol uses HTTP within the encrypted tailnet, not HTTPS. The Dart HTTP client accepts only literal 100.64.0.0/10 addresses and rejects redirects and proxies. No broad Android cleartext exception is added. A platform that blocks this transport will require a supported HTTPS transport in a later release.

Protocol 1 authenticates via Bearer session code; codes rotate on server start and are not persisted on mobile. The app polls authenticated state every three seconds in foreground, backs off on failures, clears stale state, and stops polling on exit or background. Optional music metadata is visible only if explicitly shared on PC. No streaming, remote commands, file transfer, or vault synchronization yet. Existing legacy screens are unchanged.

Testing: run flutter test test/live_server_client_test.dart and flutter analyze; then build and test on an actual phone with ZMT v5.4.0. Verify code rejection, expired code, connection loss, module launch/close, optional music status, app background/resume, and server stop. The new code has not been built or tested on a physical device in the assistant environment.

## Desktop v5.4.1 pairing
Create and copy a one-time invitation on the PC, optionally allow music status for that device, then use **Pair this phone** in the mobile dashboard. POST /api/v1/pair has an empty body and X-Pairing-Code header. The server returns a unique device token; mobile stores it with its exact URL in FlutterSecureStorage. Reopening the screen reconnects with the saved token. Session-only connection remains available. Revoke on PC to invalidate credentials, including active event streams; forgetting on phone only removes the local copy. Music status requires both per-device permission and the PC session switch. This is still read-only and uses literal Tailscale IPv4 HTTP. No broad cleartext exception or TLS bypass. Flutter/physical-device verification pending.

## ZMT 5.4.2 / Media Player 1.5.1
Open the updated desktop Media Player, pair the phone, enable the device's streaming and/or PC control permissions, and enable corresponding session switches. Live Music is reached from the Live Server dashboard. Library GET /api/v1/music/library?q=&offset=0&limit=50 returns opaque session-scoped track IDs. GET /api/v1/music/stream?id=... supports a single byte range and requires the Authorization header. POST /api/v1/music/control?action=play|pause|next|previous|seek|play_track with optional value or id, empty body, requires separate control permission. Music status needs the existing status grant. Phone playback is screen-scoped and pauses/stops on exit or background; do not run legacy music simultaneously (just_audio_background supports one player). No transcoding, offline caching or mobile playlists in this release. Existing platform HTTP restrictions may affect playback; no security bypass. Test both platforms and revocation on real devices before release.

## Desktop v5.4.3: Notes and Quick Send
Install Notes 1.2.1 and open it on PC. Notes must be in the Mobile folder or a subfolder, and be no more than 100,000 characters. Grant notes read and optionally edit, and turn on corresponding desktop session switches. Edits include a revision; local unsaved edits or stale revisions cause HTTP 409. No remote deletion. Quick Send uses the dedicated Live Server Inbox and Outbox (not the independent legacy Quick Send server). Open the folders on PC first. Enable outbox downloads or inbox uploads per device and session. Files max 20 MiB, ASCII filenames with safe characters; uploads get a unique prefix and never execute. Mobile screens use file picker for upload and save-file for download. No automatic bidirectional sync, background transfers, or broad filesystem access. Test permissions, conflict, file picker behavior and transfers on actual devices; no Flutter build was run here.

## Desktop v5.4.4: Live System Monitor
Grant a paired device hardware read permission and enable aggregate system monitor sharing on PC. Optional NVIDIA driver telemetry needs its own session switch. GET /api/v1/hardware returns CPU, RAM, aggregate adapter byte rates, fixed-drive capacity and optional NVIDIA GPU utilization, temperature and VRAM. Missing values are null, not zero. Server samples on demand with a three-second shared cache; mobile polls every three seconds in foreground, clears stale readings/history on errors or backgrounding, and backs off to eight seconds on errors. No process names, process controls, CPU temperatures or AMD/Intel GPU telemetry. Desktop System Monitor does not have to be open. Temporary session codes are denied. Test on physical devices; no Flutter or Windows runtime test was performed here.

## Desktop v5.4.5: Remote AI Chat
Start Ollama on PC and install a model. Enter its exact name in the Live Server page, toggle AI chat for a paired device, and enable session sharing. Open Live AI Chat from the mobile dashboard. One approved local model only; the phone cannot provide a URL, key, system prompt or tools. GET /api/v1/ai/models; POST /api/v1/ai/start JSON {model,messages}; GET /api/v1/ai/result?id=...; POST /api/v1/ai/cancel?id=... with empty body. Poll partial text roughly every 700 ms; no SSE. Only the device that owns the job can read/cancel it. One generation at a time, three-minute desktop timeout. Closing the screen requests cancellation; if unreachable the server timeout applies. Conversation history is session-only and not merged into desktop chat history. Test permission, revoke, model unavailable, streaming, cancellation, concurrent phones and transport on real devices. Flutter compilation not performed here.

## Desktop v5.4.6: Live Gaming
Build Gaming Hub 1.3.1 and Emulator 1.0.1 with the updated SDK. Open the relevant module on PC, grant Games/Roms read and optionally launch requests to the paired device, enable matching session switches. GET /api/v1/gaming/library?kind=games|roms&q=&offset=0 returns at most 50 entries with opaque IDs. POST /api/v1/gaming/request?kind=...&id=... queues one request for two minutes; local PC review required. No arbitrary executables, ROM paths, launch arguments or remote save-folder writes. Gaming Hub retains its normal launch confirmation. Save transfers use existing Live Quick Send Inbox/Outbox with manually prepared backups and manual restore. Test both catalogs, expiry, revoke, local approval and rejection. Flutter and Windows runtime testing pending.
